1. What the system does

The system reads vehicle number plates from video (recorded files or live RTSP cameras), records every detection in a database with the camera's location, and reconstructs where each vehicle travelled across a network of cameras.

CapabilityWhat it means in practice
Automatic Licence Plate Recognition (ALPR)Finds vehicles, finds their plates, reads the plate text with a neural OCR model, and stores the result.
Multi-camera processingFour configured camera sites (India Gate, Connaught Place, Karol Bagh, Kashmere Gate). Each takes an uploaded video or a live RTSP stream. Uploaded videos are processed one after another; RTSP streams all run together and keep running until the session is stopped.
Camera managementCamera sites are added and removed from the dashboard: adding asks for the place, latitude and longitude, and the new camera immediately gets its own upload/RTSP controls, feed panel, map marker and queue position. Cameras can also be renamed in place. Removing takes its feed with it and keeps its recorded detections.
Trajectory reconstructionFor any plate, orders its sightings in time and draws the route on a map with distances, travel times and speeds.
Vehicle profilesOne summary per vehicle: YOLO vehicle class, body colour, thumbnails, first/last seen, cameras visited, visit history.
Vehicle searchType a description (“white cars after 9am today at India Gate”) and see matching vehicles; click through to their trajectory.
Traffic heatmap2-D map coloured by where vehicles are now (or by total traffic per camera).
Blacklist alertsPlates on a watch list (e.g. DL7CD5017) raise a red alert on the dashboard and in the live processing log.
Live camera wallFour feeds per row of each camera's annotated video, streamed smoothly to the browser; a fifth camera starts the next row.
REST APIEvery capability is also available as HTTP/JSON endpoints for other software.

3.2 Data flow for one vehicle

 1. Frame read from video/RTSP                     (OpenCV + FFmpeg)
 2. Vehicles detected in the frame                 (YOLOv8n, TensorRT FP16)
 3. Each vehicle given a persistent track ID        (ByteTrack)
 4. Plate located inside the vehicle crop           (custom YOLOv8 plate model)
 5. Plate image cleaned and enlarged                (CLAHE, gamma, sharpen, upscale)
 6. Plate text read                                  (PARSeq-tiny, TensorRT)
 7. Text validated against Indian plate formats     (regex + OCR correction)
 8. 5 readings of the same track voted together     (OCR fusion)
 9. Duplicate check (same plate within 30 s)        (Levenshtein distance ≤ 2)
10. Plate colour → registration category; direction; YOLO class; body colour
11. Images and thumbnails saved to disk
12. Row inserted into vehicle_events; vehicle profile updated in same transaction
13. Blacklist checked → alert in live log / dashboard
14. Dashboard and API read the database; trajectory rebuilt on demand

5. The ALPR pipeline (computer vision and AI)

Implemented in scripts/run_pipeline.py with components under src/. Each stage is described with the technology it uses and why.

5.1 Frame capture — OpenCV + FFmpeg

src/capture/frame_capture.py. OpenCV's VideoCapture (backed by FFmpeg) opens local files, RTSP/RTMP/HTTP streams, or webcams.

  • Recorded files are read frame by frame in order (frame_skip: 1 — every frame).
  • Live streams use a background reader thread that keeps only the newest frame, so latency cannot build up when processing is slower than the camera.
  • Automatic reconnection (5 retries) and stall detection (10 s without a frame).

5.2 Vehicle detection — YOLOv8 + TensorRT

YOLO (“You Only Look Once”) is a single-pass convolutional neural network that outputs bounding boxes and class labels. The vehicle detector is YOLOv8n pretrained on the COCO dataset; only the classes car, truck, bus, motorcycle are kept.

SettingValue
Model filemodels/vehicle_detector/yolov8n.engine
Input size480 px
Confidence threshold0.5
PrecisionFP16 (half precision)

TensorRT is NVIDIA's inference optimiser. A trained model (.pt / .onnx) is compiled once into an .engine file tuned for this exact GPU: layers are fused, kernels are chosen for the hardware, and weights run in 16-bit floating point. On Jetson this is several times faster than running the PyTorch model directly.

5.3 Vehicle tracking — ByteTrack

src/tracking/vehicle_tracker.py uses ByteTrack from the Supervision library. It links detections in consecutive frames into tracks, giving each physical vehicle a stable track ID. This is what lets several OCR readings of the same car be combined, and lets a vehicle be stored once per pass instead of once per frame. Lost tracks are kept for 60 frames; the IoU matching threshold is 0.5.

5.4 Plate detection — custom YOLOv8

src/detection/plate_detector.py. A YOLOv8 model trained on number-plate images runs inside each vehicle crop (not the whole frame), which makes it faster and more accurate. Engine models/plate_detector/best.engine, input 320 px, confidence 0.4.

5.5 Plate preprocessing and super-resolution

src/preprocessing/plate_preprocessor.py and src/enhancement/super_resolution.py:

  • CLAHE (Contrast-Limited Adaptive Histogram Equalisation) — boosts local contrast so characters stand out.
  • Adaptive gamma — brightens dark/night plates, tames glare.
  • Sharpening — crisper character edges.
  • Upscaling — plates narrower than 180 px are enlarged (OpenCV bicubic on Jetson; Real-ESRGAN is supported where PyTorch allows it).

5.6 OCR — PARSeq on TensorRT

src/ocr/parseq_tensorrt_engine.py. PARSeq (Permuted Autoregressive Sequence model) is a transformer-based scene-text recogniser. The tiny variant, fine-tuned on plates, is compiled to TensorRT (models/ocr/parseq_official_tiny.engine, input 32×128).

  • Uses TensorRT 10's named-tensor API and execute_async_v3.
  • PyCUDA allocates the GPU input/output buffers once and reuses them (avoids per-call allocation cost).
  • If the engine was built for a different GPU, it is rebuilt automatically for this one and saved.
  • Alternative backends selectable in config: RapidOCR (ONNX Runtime, CPU), EasyOCR, PaddleOCR, TrOCR.

5.7 Validation, fusion and de-duplication

StepModuleHow it works
Plate validationvalidation/plate_validator.py, ocr/ocr_postprocessor.pyRegular expressions for Indian plate formats (e.g. DL8CA1234) and BH series; common OCR confusions (O/0, I/1…) are corrected before re-validating.
OCR fusionvalidation/ocr_fusion.pyCollects up to 5 readings per track and votes; at least 2 identical readings and confidence ≥ 0.55 are required. Then an OCR pass on the best upscaled crop may replace the result if more confident.
Duplicate filterdatabase/duplicate_filter.pyThe same plate (or a plate within Levenshtein edit distance 2) within 30 s is not stored twice — catches a vehicle whose track split in two.

Adding and removing camera sites

Operators manage the camera list from the dashboard (Add camera, and Remove camera on each card) or over the API (POST /trajectory-api/cameras, DELETE /trajectory-api/cameras/{id}).

  • Adding asks for the place, latitude and longitude. Coordinates are required, not optional: a camera without them records events that no map or heatmap can place. The new camera is complete at once — its own upload/RTSP controls, its own panel on the camera wall, its own marker on the map and heatmap, and the last place in the processing queue. It just has no source yet.
  • Renaming changes only the label. The camera keeps its id, coordinates, queue position and source, and events already recorded keep the name they were stamped with — they record what the site was called when the vehicle passed.
  • Removing takes the site's configuration, its uploaded video and its last preview frame, so no still image is left behind on the wall. Detections it already recorded are kept — they are history and carry their own camera id and coordinates, so past trajectories still plot. The last camera cannot be removed.
  • Where it is stored: camera_config.yaml is hand-written and heavily commented, so it is never rewritten. The operator's camera list lives beside it in config/cameras_runtime.yaml, written only by code; when present it replaces the shipped camera list, while processing and trajectory still come from the main file. Delete it to go back to the shipped cameras.
  • Neither operation is allowed while a session is running.

Why recorded files run one at a time

The Jetson has one GPU and the pipeline already uses it fully. Running cameras in parallel would make every camera slower. Sequential processing also means, for the demo, that timestamps increase camera by camera.

Why live streams run together

A live stream carries what is happening now. Making camera 2 wait its turn would not delay its footage, it would discard it: every vehicle passing camera 2 during camera 1's turn would simply never be seen. So every RTSP camera starts at once, on its own thread, and keeps running until the operator presses STOP — no time limit.

They share one set of GPU models through a lock (PipelineModels.shared()), because a TensorRT execution context can only process one inference at a time. Decoding, tracking, OCR fusion and database writes still happen in parallel, which is where a live stream spends most of its time. Measured on this device with four cameras at once: about 7.9 fps each, roughly 31 fps in total, against about 20 fps for a single camera alone.

A queue may mix the two: the uploaded videos run through first, then the live cameras start together and stay up.

Processing sessions

Each START creates a processing session id (e.g. 20260913-092351-5045e9) stored on every detection. Sessions can be viewed separately and deleted (events, images and profiles are updated).

7.5 Schema migration

SQLAlchemy's create_all() creates missing tables but never changes existing ones. db._migrate_schema() therefore inspects the live table and runs ALTER TABLE vehicle_events ADD COLUMN … for any missing column, one statement per transaction. It is idempotent (safe to run on every start) and tolerates two processes migrating at the same time. When vehicle_profiles is created for the first time, profiles are built from existing history automatically.

7.6 Representative SQL (what SQLAlchemy generates)

All detections of one plate, oldest first (trajectory)

SELECT * FROM vehicle_events
WHERE plate_number = 'DL8CA1234' AND processing_session IS NOT NULL
ORDER BY timestamp ASC;

Vehicles seen at two or more cameras

SELECT plate_number,
       COUNT(DISTINCT camera_id) AS camera_count,
       COUNT(id)                 AS detection_count,
       MIN(timestamp) AS first_seen, MAX(timestamp) AS last_seen
FROM vehicle_events
WHERE processing_session IS NOT NULL
GROUP BY plate_number
HAVING COUNT(DISTINCT camera_id) >= 2
ORDER BY camera_count DESC, detection_count DESC;

Statistics per camera

SELECT camera_id, camera_name, COUNT(id) AS detections,
       COUNT(DISTINCT plate_number) AS unique_plates, AVG(confidence) AS avg_confidence
FROM vehicle_events WHERE processing_session = :session
GROUP BY camera_id, camera_name;

Delete a processing session

DELETE FROM vehicle_events WHERE processing_session = :session;
-- then the affected vehicle_profiles are rebuilt from the remaining events

Description search (e.g. “white commercial trucks”)

SELECT * FROM vehicle_profiles
WHERE vehicle_color IN ('White') AND vehicle_class IN ('truck')
  AND vehicle_type IN ('Commercial')
ORDER BY last_seen DESC;

8. Trajectory reconstruction and GIS

Package src/trajectory/. Works on plain data, not on the database, so the logic is fully unit-tested.

  1. Group into visits — consecutive detections at the same camera within 300 s become one visit; a genuine return to a camera later is a new visit.
  2. Order — by timestamp; if any timestamp is unusable, by camera queue order (order_by: auto).
  3. Measure each leg between consecutive visits:
    • Distance — Haversine great-circle formula on Earth radius 6371.0088 km.
    • Bearing — initial compass bearing (used to rotate map arrows).
    • Duration and speed = distance ÷ time (only when both exist and time > 0).
  4. Output — ordered points, legs, summary figures, and GeoJSON (RFC 7946): one LineString for the path plus one Point per visit.
Coordinate order: GeoJSON uses [longitude, latitude]; Leaflet uses [latitude, longitude]. The conversion happens in one place (trajectory/geojson.py).

Coordinates always come from the camera location stored on each detection — no route is hard-coded.

10. Vehicle profiles and body-colour detection

10.1 Profiles

src/database/vehicle_profiles.py. Each detection is folded into the plate's profile inside the same database transaction, isolated in a savepoint so a profile error can never lose the detection. The same fold function can rebuild a profile from all events, so live and rebuilt profiles are identical.

  • Class and colour are majority votes, ignoring “Unknown”.
  • Images come from the highest-confidence detection.
  • Out-of-order detections trigger a rebuild so history stays in time order.
  • Deleting a session rebuilds affected profiles; a profile with no events left is deleted.

10.2 Body-colour detection

src/classification/vehicle_color.py — a fast HSV (Hue-Saturation-Value) colour heuristic, no extra model. Supported: White, Black, Silver, Gray, Blue, Red, Green, Yellow, Brown, Orange.

  1. Skip the top 35% of the vehicle box (windscreen and roof reflect sky) and the edges.
  2. Downscale to ~64 px wide and convert BGR → HSV.
  3. If ≥ 25% of pixels are saturated (S ≥ 55, V ≥ 50) the vehicle is coloured: vote on hue bands (brown = dark orange).
  4. Otherwise it is achromatic: median brightness decides White (≥180) / Silver (≥130) / Gray (≥70) / Black.

Measured accuracy: 30 of 36 hand-labelled vehicle crops from this site's videos. Cost ≈ 0.5 ms per stored vehicle. Thresholds are configurable under vehicle_color: in config.yaml.

12. Blacklisted vehicles

src/alerts/blacklist.py, list stored in config/blacklist.yaml (currently DL7CD5017).

  • Matching — case-insensitive, ignoring spaces and dashes; exact otherwise.
  • Live alert — when the pipeline stores a blacklisted plate, the processing log shows “ALERT: BLACKLISTED vehicle … detected at <camera>” and a warning is logged.
  • Dashboard banner — red alert at the top listing each blacklisted plate, last camera, time and number of sightings (from all sessions).
  • Management — “Blacklisted vehicles” section to add (with reason) or remove plates; view image and trajectory.
  • Badges — red BLACKLISTED badge on search results and trajectory card.
  • The file is re-read when it changes, so edits apply even during a running session.

14.3 Smooth live video — MJPEG preview server

  • The pipeline's LiveFramePublisher writes each camera's annotated frame to data/live_frames/<camera>.jpg at up to 15 fps, downscaled to 960 px, encoded on a background thread so ALPR is not slowed.
  • The preview server (Python http.server, port 8765) streams those files as MJPEG (multipart/x-mixed-replace), which browsers play natively in an <img> tag.
  • The player HTML never changes between Streamlit reruns, so the video keeps playing continuously.
  • Measured: 14.1 fps (recorded video) and 13.6 fps (RTSP) delivered to the browser, versus 0.5 fps before.

20. Known limitations

  • Vehicle search is rule-based, not a large language model; it understands the vocabulary in section 11, not arbitrary sentences.
  • Body colour is a heuristic (30/36 on real crops); watermarks, reflections and partly hidden vehicles can mislead it.
  • Blacklist matching is exact; an OCR misread of a blacklisted plate will not trigger an alert.
  • Uploaded videos are processed one at a time, so a long queue of recordings takes the sum of their runtimes. Live cameras do run together and continuously; they share one GPU, so each stream runs slower than a single camera would.
  • Demo speeds look unrealistic (hundreds of km/h) because one video is replayed at sites kilometres apart; real cameras give real travel times.
  • Clock sync: trajectories order by timestamps, so live cameras/devices need NTP time synchronisation.
  • The camera wall uses a second port (8765); it must be reachable from viewing computers.
  • At process exit PyCUDA may print an “Exception ignored” message; it does not affect data or the running dashboard.
